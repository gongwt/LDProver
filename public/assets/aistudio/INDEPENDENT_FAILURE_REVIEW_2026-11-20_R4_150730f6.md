## 1. 验收意见

**R3 的区域外证明边、C++ 无效 DAG 子边、合法子局面无法反序列化、两端证书无法交叉读取等原反例均已有实质修复。原题及原配置下，TS 复现 7 题已定论，C++ 原生求解得到 6 题已定论。** TS 生成的 7 份证明全部通过 C++，C++ 在标准小题上生成的 6 份证明也全部通过带题目及上下文绑定的 TS 校验。差的一题是 p042，原生搜索在同一节点上限内没有产出证明。

仍建议保留两项验收阻断。第一，调用者要求验证某道原题时，现有入口可以对规则不同的证明或越区试下后的子局面返回 PASS。第二，双端对完整文件中哪些字段经过核验给出了不同答案，C++ 的成功回执还会返回另一个摘要。下文列出复核这两项问题及 16 个 TS UNKNOWN 的棋局与代码入口。

## 3. 两个会改变“证明了什么”的入口问题

### P1　原题绑定接受了超出局部题规则的到达轨迹

在 p001 同型原生夹具中，`dd` 明确在 region 外。从原局走 `B[dd] W[pass] B[ba]`，调用 `solveFromPosition`，生成带轨迹的单叶胜证。TS 用完整的原题及上下文校验得到 PASS，C++ 用 `check --proof … --problem p001fixture.json` 同样 PASS。把越区点放在证明边上则会触发 F1 的 `LP-S11`。

p005 显示这一区别会直接影响读者理解。按题目默认禁劫，从原根求解为 `UNKNOWN(ko_dependent)`。手动下 `B[ca]` 时，棋规层确实提走了白 `ba`，并返回 `isKoCapture=true`。在原禁劫上下文中从此处求解，得到 1 节点 `PROVEN_WIN`。TS 完整原题绑定与 C++ 文件校验均 PASS。**这份证书可以证明给定子局面上的关键子已被提走。它不能充当原根满足禁劫见证条件的证书。** 此处的劫权是存在性见证的约束，不能据此删除全称节点中的对方合法提劫应手。

实现原因可定位到 TS `proofChecker.ts:824`、C++ `proof_checker.cc:1635`。两端轨迹回放调用棋盘层落子，证明边另行应用 region 与角色规则。工作台 `App.tsx:413` 的试下入口也调用棋盘层。建议验证请求显式携带所求命题，例如“原根结论”“指定轨迹后的局面”“自由试下后的条件结论”。原根请求必须匹配 `rootKind=initial`。题内轨迹每一步应核对 region、轮次和历史，并记录受限提劫的角色与用途。自由试下可以保留，通过时明确返回其条件范围。验收时并列运行 p001 的合法 `ba`、越区 `dd` 和 p005 的受限 `ca`，检查不同用途各自的返回值。

### P1　TS 只传原题，会漏掉关键子和劫权

使用 p001 正常证书，保持盘面、轮次、区域、墙完全一致，只把外部题目的黑关键子从 `bb` 改成 `da`。传 `{problem}` 得 PASS；再传从该题推导的 `context` 得 `LP-P01`。更直接的对照是 p005。**开放攻击方劫权时，2 节点证出 `ca`；把该文件交给默认禁劫的 p005，仅传 `{problem}` 仍 PASS。** 带默认上下文得到 `LP-P01`，带开放劫权上下文正常通过。

在 `proofChecker.ts:898` 和 `:924`，盘面比较与目标、令牌、规则比较各有独立的可选分支。调用者只传原题，类型系统仍视为有效的绑定请求。建议面向使用者提供“按该题默认契约验证”的完整入口，由可信侧统一推导上下文；规则变体必须显式给出。返回结果携带已验证的目标、劫权及原根/子根身份。同盘异目标、同题异劫权、原根与合法子根应成为三个独立对照。

## 6. 原生搜索、内存与构建

**C++ 可以读懂 p042 的 TS 证明，自身搜索没有走到第一个闭合节点。** 全新 Release 构建后，用原生解析器读 16 个真实 JSON，将配置显式设为与 TS 相同的节点、深度和扩窗基数。逐题比对双端解析所得的黑白子、墙、region、轮次、根 Zobrist、令牌及分组、攻守目标与双方劫权，16 题均一致。16 题全部在 3500 节点返回 UNKNOWN，均为 0 个 DAG 节点、0 次 RZ 剪枝。另将 7 个 SRS 内置题的实际棋子、墙、region、令牌与劫权逐项传入原生 API，保持其与 TS 相同的模型。两端在标准题的实际结果见下表。

| 标准题 | TS 节点 | C++ 节点 | 结果及验证 |
|---|---:|---:|---|
| p001 | 2 | 5 | WIN ba，双向互验通过 |
| p002 | 2 | 2 | WIN ca，双向互验通过 |
| p003 | 10 | 11 | WIN db，双向互验通过 |
| p004 | 12 | 13 | WIN pass，两端各 3 次 RZ，双向互验通过 |

原生 `dfpn_solver.cc:409` 在每次递归调用重新建立子节点向量，`:443` 重置扩窗与代表证明状态；TS 在 `dfpnSolver.ts:1258` 按历史取回前沿。C++ 的 `ScoreMoveFastCapture`、窗口大小、阈值和 PASS 代表手选择也与 TS 不同。上述为可定位的实现差异，单项各占多少耗费尚待分量实验。最有辨别力的指标是同一历史再次进入时恢复了多少子项、首次找到可重放见证用了多少节点。原生 p042 在零 DAG 阶段已经耗完预算，优先测这一段，比先优化证书序列化更贴近失败位置。

**P2　内存限额在原生搜索最需要它时可能一直计为零。** p042 在 TS 设置 0.005 MiB 后，第 1 个节点即返回 `UNKNOWN(memory_budget)`。C++ 直接设置约等价的 5242 字节，仍运行至 3500 节点，返回 `node_limit`。其计量在 `dfpn_solver.cc:23` 仅统计 DAG 与 TT，当前沿和递归位置对象已分配而 DAG/TT 为空时，这两项不足以代表搜索占用。另有 CLI 参数问题，`tprover_main.cc:130` 用整数解析，`--memory-budget 0.005` 会变为 0，而 0 会关闭该检查，实跑同样耗到 3500。建议先确定单位和整数/小数契约，非法值直接退出 2；再按实际容器容量统计当前和峰值，将前沿、历史、状态副本纳入核算。TS 同样使用固定权重，当前结果只验证该阈值可触发，未证明 512 MiB 是进程内存硬上限。

**构建可通过，默认依赖安装存在可复现的先决问题。** C++ 使用 AppleClang 21.0.0.21000334 在新目录完成 CMake Release 编译及原生运行。前端以同一 HEAD 的临时干净副本安装。默认 npm 解析报 `ERESOLVE`，项目声明 esbuild `^0.25.0`，本次解析到的 Vite 8.3.8 可选 peer 需要 `^0.27.0 || ^0.28.0`。仅在临时副本使用 `--legacy-peer-deps --ignore-scripts` 后，TypeScript 7.0.2 的 `npm run lint` 与 `npm run build` 均退出 0。Vite 提示配置中的 `__dirname` 及超过 500 kB 的产物。本轮没有运行浏览器交互 E2E。

## 7. 建议的修复顺序与验收标准

1. **先固定验的命题和文件。** 原题默认契约自动派生上下文，入口显式区分原根、指定子根和自由试下。完整/紧凑编码分别明确必验字段，成功回执绑定输入摘要，推荐着由已核验的根见证导出。用 §3、§4 的成对样例和现有 7 份正例共同验收。
2. **在 p031 上做单变量搜索实验。** 维持原题、原始 153 点区域、SSK、劫权与 3500 节点上限，先为 `sr` 后的 `os`、`rs` 和未展开 77 手记录各自的闭合、重放失败或未访问原因。只改变一项应手调度策略，与 62/141 的对照比较，并以 p042 保证原成功路径仍可验。到限保存覆盖清单；仅当 141 项全部闭合、封装回原根且两个 checker 通过时登记整题已解。
3. **再分离原生前沿丢失与排序的影响。** 用 p042 固定规则与数值配置，先比较首次代表证明、重复进入同一历史、重建的子项数；然后只引入一种前沿恢复策略做对照。p222 留作“尚无代表证明”的样本，p005 留作禁劫负对照。分别记录节点、实际内存、根结论、文件摘要和跨端回执。
